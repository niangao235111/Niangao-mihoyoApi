# 原神祈愿记录与分析接入方案

日期：2026-10-18。以下保留最初设计。当前已实现后端 7 个接口、两张表和独立前端祈愿页签；实施细节与取舍见 [接口与升级说明](genshin-wish-api.md)。真实账号授权仍待本人指定会话或页面测试。

## 现有代码检查结论

当前后端提供登录、关联账号、角色总览、角色装备、工作台会话、档案保存与安全验证接口，未发现祈愿记录 Controller、同步 Service 或玩家祈愿记录表。

文档中提到的旧 `gacha_items` 是角色 / 武器物品目录，不是玩家抽卡历史，不能据此判断已实现抽卡功能。

固定依赖 JAR 已包含 `uigf.mihoyo.game.genshin.gacha.GachaClient`、`GachaClientBuilder`、`GachaLogPage` 与 `AuthKeyApiClient`。因此有可复用的客户端基础，但 SDK 包含方法不等于业务已接通；需核对固定版本的方法签名及 JSON 兼容性。

## 参考依据与需要验证的部分

1. [UIGF SDK 原神接口定义](https://github.com/UIGF-org/mihoyo-api-sdk/blob/main/src/game-genshin.tsp) 声明国服祈愿记录地址：`https://public-operation-hk4e.mihoyo.com/gacha_info/api/getGachaLog`。它和角色战绩是不同接口。
2. [genshin.py 祈愿客户端](https://github.com/seriaati/genshin.py/blob/master/genshin/client/components/gacha.py) 使用独立 `authkey`，按 `end_id` 拉取记录，每页设置 20 条；其当前 Cookie Token 换 AuthKey 方法明确限定海外区域，不能直接当作国服方案。
3. [UIGF 国服 Token 资料](https://github.com/UIGF-org/mihoyo-api-collect/blob/main/hoyolab/user/token.md#通过stoken获取账号auth-key-b) 收录 SToken 调用 `/binding/api/genAuthKey`、指定 `auth_appid=webview_gacha` 的方案。它是候选链路，不代表当前 SToken V2、官服与 B 服均能成功，必须实测后再承诺“一键同步”。不要误用米游社账号 Auth Key A。
4. [genshin.py 卡池模型](https://github.com/seriaati/genshin.py/blob/master/genshin/models/genshin/gacha.py) 区分新手、常驻、角色、武器、集录祈愿，保留原始卡池类型。
5. [UIGF v4.2 标准](https://uigf.org/zh/standards/uigf.html) 提供多账号抽卡记录交换结构，包含原始类型、统计分组、记录 ID 与时区，适合作为备份导入导出格式。

以下接口、数据库、限流和页面安排是针对本项目提出的设计，不是上游接口保证。

## 用户流程

优先尝试复用现有米游社工作台登录，实现：

登录 → 选择已绑定的国服角色 → 点击同步祈愿 → 后端获取祈愿专用 AuthKey → 分页读取 → 增量写入 MySQL → 页面查询数据库展示。

需要保留两个后备入口：

- 粘贴本人从游戏祈愿历史页面取得的记录链接。后端只提取允许的授权参数，构造固定上游请求，不访问用户提供的任意 URL。
- 导入已有 UIGF 记录备份，补充此前已保存的历史。初版支持明确标注的 v4.2 原神部分；其他版本需独立转换器，不能一律当作同一结构解析。

自动换取 AuthKey 失败只影响祈愿同步，不删除现有工作台会话或角色档案。分别提示网络错误、凭证失效、授权失败与需要用户操作；不能假定现有战绩 GT3 证明适用于祈愿授权场景。

AuthKey 官方 TTL 目前没有在本次资料中得到可靠确认，不写死“永久有效”或“24 小时有效”。仅加密缓存于 Redis，建议本地缓存上限 30 分钟；上游判定失效时清除并重新授权，本地 TTL 仅为本项目策略。

## 页面设计

在工具箱增加“祈愿分析”页签，保持账号切换体验一致。

- 顶部：UID、官服 / B 服、最近同步时间、同步状态，以及“同步记录”“导入”“导出”入口。
- 核心数据：已保存总抽数、五星 / 四星数量、最近五星之后已记录抽数、有效区间内五星平均间隔。
- 卡池切换：角色活动、武器、常驻、新手、集录；角色活动 301 / 400 合并统计，但保留原始类型。
- 五星时间线：角色 / 武器名称、获得时间、两次五星之间抽数；点击展开明细。
- 记录表：按卡池、星级、时间筛选，使用游标分页。
- 明确展示最早 / 最晚记录时间和“历史可能不完整”；空数据需区分尚未同步、确实无记录、同步失败。

初版不做全服欧非排名，也不根据不完整数据断言“大保底”“下次必出”或“是否歪”。UP 判定需要对应历史卡池资料；无法确定时返回未知。武器定轨等状态不能仅凭抽卡结果完整恢复。

## 同步与统计规则

1. 首次同步逐卡池读取上游当前仍可返回的记录；上游不可读取且用户没有备份的旧记录，无法凭空恢复。本次不承诺固定历史保留月数。
2. 按 `end_id` 游标翻页，不依赖页码递增；每页校验 UID、region 与当前工作台所选账号是否匹配。遇到空页、重复游标、响应超限立即停止或报错。
3. 记录 ID 在 JSON 中统一使用字符串，避免 JavaScript 大整数精度丢失；数据库可用 DECIMAL(20,0) 排序，不能只按时间排序。同秒多抽仍按 ID 排序。
4. 数据按账号与记录 ID 唯一写入，重复同步不增加抽数。卡池抓取可能重叠，因此即使遍历 301 / 400，也必须去重后统计。
5. 增量同步直到遇到已连续覆盖区间；部分失败要记录未完成区间，不能只凭最大 ID 永久跳过旧缺口。提供显式补全同步。
6. 每页短事务落库，保留已经成功的数据；不要让长时间上游网络等待占据数据库事务。失败标记“部分成功”，不清空旧记录。
7. 建议同账号同一时间只运行一项任务，Redis 锁带随机所有者与续租，释放时比较所有者。服务重启后把失联任务标记中断，允许补同步。
8. 面向现有 2 核 2 GB 部署，建议单实例工作线程 1～2 个、全局有限队列；页间初始间隔 500～1000ms，作为可调整策略，不宣称上游保证接受该速率。
9. 网络瞬断按页有限重试；429 / 上游限流单独退避，不轮换 IP 绕过限制。无进展、授权失效、用户取消或任务超时要停止。
10. 统计只针对已保存记录；第一条五星前的区间可能截断，不能当作完整五星间隔参与平均。记录覆盖状态按卡池维护；后续发现新缺口需降低可信度。

## MySQL 与 Redis 分工

复用 `ng_genshin_account` 标识账号，不复用角色表保存抽卡明细。建议只新增两张表：

| 表 | 主要内容 |
| --- | --- |
| `ng_genshin_wish_record` | account_id、上游 record_id、原始 gacha_type、统计 pool_group、item_id（允许缺失）、物品名称、类型、星级、数量、原始时间 / 时区、统一 UTC 时间、来源、导入时间 |
| `ng_genshin_wish_sync_run` | account_id、任务类型（同步 / 导入）、状态、各卡池游标与覆盖区间、新增 / 重复 / 失败计数、阶段 / retcode、开始 / 完成时间、是否存在缺口 |

明细唯一键 `(account_id, record_id)`，增加账号 + 卡池分组 + 记录 ID 查询索引。任务表只保存脱敏元数据，不保存 AuthKey 或原始链接。不新增每日快照，不为每次查看页面创建同步记录。

Redis 保存短期加密 AuthKey、任务锁与限流状态；MySQL 保存可恢复的进度和长期记录。统计先从数据库按账号聚合，必要时再增加可重建缓存。导入来源必须保留，导入的数据属于用户提供的信息，不作为可验证的官方排行榜凭证。

## 后端接口草案

下列为拟新增接口，不是当前可调用地址。统一前缀 `/api/workbench/genshin/wishes`，复用现有 Cookie、CSRF 与来源校验。

| 方法 / 路径 | 用途 |
| --- | --- |
| POST `/sync` | 创建同步任务，支持自动授权或提供历史链接；返回 202 与 task_id |
| POST `/sync/status` | 查询本人账号任务进度及部分成功状态 |
| POST `/sync/cancel` | 取消本人任务，保留已写入记录 |
| POST `/records` | 从 MySQL 游标分页读明细，可按卡池 / 星级筛选 |
| POST `/summary` | 查询已保存数据的统计与覆盖范围，不访问米哈游 |
| POST `/import` | 校验 UIGF 数据并幂等导入，返回新增 / 重复数量 |
| POST `/export` | 导出本人选定账号的 UIGF JSON，不含凭证 |

账号归属必须从已验证工作台会话和绑定角色确定，不能相信浏览器传入 owner_stuid。导入需逐账号校验；不属于会话的 UID 拒绝并说明原因。首次没有任何上游记录时，链接参数不能单独作为归属证明。

现有接口请求体上限 16 KiB 不适合批量导入；实施时为导入单独配置有限大小（例如初版 5 MiB）及最大记录数，应用与网关同步调整，避免放宽所有接口限制。文件完整校验通过后再分批写入；字段冲突不静默覆盖旧记录。

## 凭证与可用性处理

- 浏览器把链接放在 POST 请求体，不放本站查询串、不写 localStorage；服务端日志不记录请求体或上游完整查询 URL。
- 祈愿上游把 AuthKey 放入查询参数，必须确认 HTTP 客户端异常、访问日志、监控与链路追踪均不输出这个查询串。
- 用户链接仅解析，固定 HTTPS 上游域名与允许参数，不跟随任意重定向，避免把链接输入变成通用代理。
- 保留国服官服 / B 服限制。B 服是否可自动授权需单独实测；不因 SDK 存在方法就宣称两种渠道都已跑通。
- 数据保存后仍可查看，但必须重新获得有效的工作台会话才能访问本人档案；退出不会自动公开历史数据。

## 建议实施顺序与验收

1. 先做协议验证：核对固定 SDK、现有 SToken V2 换 AuthKey、官服 / B 服各自返回、专用 AuthKey 的首次记录查询。需要安全验证时保留人工完成入口。真实凭证不写测试夹具。
2. 完成两张表与后台同步、明细 / 统计查询；保留手动链接入口和任务进度，处理分页去重、断点与部分失败。
3. 增加前端卡池分析与时间线，以及 UIGF 导入导出。
4. 自动测试覆盖跨账号拒绝、链接编码、ID 精度、301 / 400 重叠、同秒排序、重复页、缺口恢复、超时 / 限流、过期不影响档案、文件超限及日志脱敏。

设计阶段没有修改业务；后续按用户授权完成了本地实现与测试，并在本地开发库创建两张祈愿表。尚未部署服务器或推送此次修改。
